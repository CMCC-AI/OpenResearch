# 项目新对话提交验收（2026-11-09）

## 行为与边界

此前首页先创建空会话并导航，首条消息由 ChatPanel 的内存交接 effect 发送。导航成功不能证明首条消息已被服务端接收。本次对不含附件、标注及 `/`、`!` 命令的普通问题改为先发送、后导航，覆盖普通工作模式和研究模式。

发送失败留在首页并保留问题；同一项目重试复用会话、clientTurnId 和发送配置。响应丢失时查询持久回执，只有匹配的会话、请求标识及有效回执才允许进入对话。工作空间切换后停止旧请求的后续操作。附件与命令继续使用已有共享 composer 流程。

首次隔离验收没有覆盖旧标签页。用户随后提供 `/tasks/new` 截图；在用户的实际 Chrome 中确认该标签仍加载 `assets/index-arxiv-6b9508fe24e6.js` 和 `index-UEqY4qoX.css`，与网关当前入口不同。旧页面驻留的 SPA 在页内导航时继续运行旧代码，HTTP 缓存重新校验头不会替换已经执行的脚本，这是本次反复出现旧入口的已核实原因。

普通刷新后，旧 `/tasks/new` 进入统一首页；通过真实已登录账号提交“你好”后进入 `tasks/chat_…`，消息进入记录并出现“正在思考”。之后在同一服务器浏览器可见用户再次发送的“你好啊”及完整模型回复，确认真实链路工作。未触发实验或其他科研操作。

`DeploymentUpdateNotice` 每分钟及页面重新聚焦时以 `no-store` 读取静态入口，比对已加载的 module script。发现变化后提醒保存输入并刷新，不自动刷新或发送草稿；断网和非 HTML 错误响应不构成更新。已经加载不含此检查的历史标签需要首次刷新一次，此后才具备版本提示。

会话在首条发送前进入查询缓存，并在导航时保留实时更新后的 busy/title，避免用创建时的空快照覆盖执行状态。
