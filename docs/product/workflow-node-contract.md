## P0：执行计划与展示图

`WorkflowDraftInput.tasks` / Rust `TaskSpec` 仍是执行计划的唯一任务来源。`ui/src/workflow/graph.ts` 从任务依赖派生展示图，`SystemNode.tsx` 负责系统节点外观。保存或移动展示节点不增加任务、不调用模型、不修改审批状态。

| 节点 | 标识 | 数据来源与行为 |
| --- | --- | --- |
| 专家任务 | 原任务 ID | 保留角色、简报、依赖、产物、输入绑定与控制属性。 |
| 历史输入坐标 | `:system:input` | 仅兼容旧草稿坐标，不再生成可见节点。需求由聊天提供，目标与材料固定到本次计划。 |
| 范围确认 | `:system:G1` | 显示现有 G1，无法在草稿删除或批准。 |
| 任务后确认 | `:system:G5:<taskId>` | 从 `requiresApproval` 生成，取消检查点即关闭对应任务开关；不生成虚构专家任务。 |
| 交付确认 | `:system:G4` | 显示现有交付确认；全部任务验收及结论、证据检查由现有服务端控制。 |
| 研究交付 | `:system:output` | 对应已确认研究包；成果与下载继续使用现有入口。 |

冒号不属于合法任务 ID，因此展示标识与任务标识不冲突。系统坐标保存在原 `positions` 中；上限调整为 84（40 个任务、最多 40 个检查点、4 个系统节点），专家任务上限仍为 40。旧草稿无需新增字段或数据库迁移。服务端 `into_plan` 只读取原 `tasks`，不将布局纳入批准范围。

实线仍代表原任务依赖。展示端点经过任务检查点时，边额外携带原任务的 source/target；删除该依赖仍更新原 `dependsOn`。虚线为自动派生的系统边，不可删除、重连或用来绕过确认。G5 仅控制下游任务派发；无下游任务的 G5 不额外成为 G4 的服务端前置条件，展示图保留此语义。

草稿统一显示“运行时填写 / 确认 / 生成”，不推断已批准状态。运行面板的 W1“本次任务依赖”显示系统节点，复用当前计划版本的审批记录：G5 还须匹配任务产物、哈希、大小及摘要，G4/交付还须匹配确认包的 scopeHash；证据变化和交付错误覆盖成功外观。节点详情跳转到现有人工确认记录，不增加第二套审批操作。

当前使用入口：在聊天选择方法或直接表达需求，AI 通过 `orx research workflow list/show/use` 绑定当前主会话。工作流选择页与编辑器不再填写运行目标或直接创建研究会话；“在对话中使用”只准备输入草稿。`ResearchPlan.workflowSource` 可选保存方法 id、名称及更新时间，进入新计划的批准范围；缺失时保留历史批准哈希。计划修订（`orx research plan`）默认继承上一版 `workflowSource`，绑定锁不会因修订被静默解除；只有显式 `research_use_workflow` 可以设置。专家子会话继续持久化，主聊天投影它们的原消息及任务产物，确认仍写原决定记录。

## 后续执行节点：评审边界

以下是 P1 及以后需要启动评审的方向，当前 API 不接受这些可执行节点：

- 定义使用显式、版本化的节点类型，例如 `agent`、`tool`、`route`；不能借 `role` 或自然语言简报伪装工具、分支或循环。
- 控制依赖与数据引用分别建模。大文件使用登记材料或产物引用，附版本/哈希；结构化结果声明 schema，在消费前校验。
- 定义与运行实例分离。实例保存运行输入、批准快照、节点状态与持久化输出，重启恢复不得从画布颜色反推执行状态。
- 独立分支须先定义默认路径、`skipped`、汇合与失败传播；结构化业务结论不等于执行成功，也不等于人工批准。
- 工具配置须包含操作标识、版本、参数与结果契约，并记录权限范围及副作用状态。新增真实执行能力进入批准范围和计划等价比对。
- Loop / For Each 使用独立作用域及执行标识，分清 attempt、iteration 与列表项；不能直接放开当前 DAG 的任意回边。

验收原则：旧计划和草稿保持可读可用；不支持的节点明确拒绝；任一路径不能跳过预设必需审查、实验限制及系统确认。具体实施优先级见 [节点库交接](workflow-node-library-handoff-2026-11-12.md)。
