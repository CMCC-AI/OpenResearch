# 工作流节点库补全交接（P0 已实现）

原始评估需求：核对当前工作流编排设计，判断专家节点之外需要哪些节点及其优先级。用户随后指示“继续”，本轮已实现下述 P0；P1–P3 仍待决定启动。

后续方向更新已实现：在聊天中输入、由 AI 执行工作流，并在当前聊天查看专家过程与输出。详见 [对话式工作流运行](conversation-first-workflow-plan-2026-11-12.md)。可见输入节点与独立目标表单已移除，旧坐标兼容保留；下文 P0 为此前阶段的交接记录，P1 工具与分流仍待启动。

2026-11-16 更新：节点扩展范围已经主理人确认（条件分流、汇合策略、失败兜底、阶段分组框、逐项处理、人工任务、实验节点、事件等待、有限循环；提问节点暂缓），分四批实施，P1 分流语义与固定工具首例（实验节点）按新方案执行。详见 [工作流节点扩展方案](workflow-node-expansion-plan-2026-11-16.md)。

## 实施前证据

- [画布](../../ui/src/workflow/WorkflowCanvas.tsx) 的 `nodeTypes` 只有 `agent`；左栏标题为“专家节点库”，所有画布节点均由 `draft.tasks` 转换生成。开始、系统确认与交付尚未作为节点显示。
- [前端任务模型](../../ui/src/workflow/model.ts) 和 [服务端 TaskSpec](../../src/store/research.rs) 已有 `inputs`、`requiresApproval`、`gateDownstream`、`maxRework` 对应字段；不能继续把这四项写成尚未实现。
- `Study::ready` 要求所有直接前置任务通过产物验收，再检查人工放行和阻塞结论。这能表达依赖及门控，尚不能直接表达互斥分支的跳过、动态逐项任务与分支汇合。
- [已有组件提案](research-workflow-components-plan-2026-11-11.md) 已论证非 Agent 组件的必要性；其中现状与阶段描述应以本次核对及当前代码为准。现有有界返工不等于通用 Loop 容器。

## 建议的节点体系

| 组件 | 解决的问题 | 优先级与提供方式 |
| --- | --- | --- |
| 输入与交付 | 明确目标、材料、参数、最终成果的边界 | P0，系统节点；方法保留输入声明，具体值在运行时绑定，系统批准不可删除绕过 |
| 人工检查点 | 确认方案、补充信息、决定继续 | P0，先展示现有任务后确认及系统确认；独立人工任务需新增持久化暂停与恢复语义 |
| 固定工具 | 明确执行材料解析、检索、去重等操作 | P1，先选已有可调用契约支持的一个真实操作，记录版本、参数、输入输出与失败 |
| 条件分流 | 根据结构化结果走不同后续路径 | P1，独立路由；先定义 skipped、默认分支及汇合，现有阻塞门控不能直接冒充 If/Else |
| 逐项处理与汇总 | 对运行时得到的论文或数据列表逐项执行 | P2，For Each 容器与汇总，声明并发、顺序、部分失败策略 |
| 有限循环 | 只重复写作—审查—修订等指定步骤 | P2，局部容器；独立轮次、产物版本、退出条件、轮数与预算边界 |
| 脚本与子流程 | 自定义计算及复用稳定方法 | P3，具体场景推动；脚本采用独立执行契约，子流程固定输入输出与版本 |

专家库应成为“节点库”中的一个分组。重试、超时和并发上限保留为运行属性；普通 DAG 并行依赖不要求另放并行开始节点。

## 本轮 P0 范围（已实现）

目标：让用户能在画布上看懂研究从哪里输入、在哪里暂停、怎样交付，并为后续非 Agent 执行节点建立兼容模型。实现限于 P0；P1–P3 另行启动。

1. 将节点库按专家任务、流程控制、输入与交付分组。只开放已经支持的入口，未实现类型不允许保存为可运行配置。
2. 显示输入、G1、任务后确认和 G4/交付节点。定义系统节点与任务依赖的映射；不得将展示节点序列化为虚构专家角色，也不得创建第二套批准状态。
3. 右侧区分系统节点、专家任务与现有控制属性；明确已有门控仅表示通过或阻塞。为后续独立执行节点评审类型及数据契约，不在此轮接入分支、工具或循环执行。

验收：

- 旧草稿打开、编辑、保存和提交仍得到相同任务及依赖；布局往返保持系统节点与任务节点位置，不引入伪任务。
- G1 批准前无任务派发；任务后确认与 G4 的节点展示准确反映既有批准记录和实际产物版本，刷新后状态一致。
- 无项目的通用方法不持有某次运行的具体目标或材料；运行输入依旧通过提交流程绑定。
- 全局与项目入口在宽屏、窄屏和折叠侧栏下可操作；使用隔离 slot 验证，按 CI 要求检查并重建 `ui/dist`。

## 下一轮 P1 建议（未启动）

目标：支持一种可审计的固定工具操作及基于结构化输出的条件分流，使“发现输入不足后补处理”能够由引擎明确执行。

1. 先选择现有工具契约能覆盖的真实材料处理案例，确定其输入、输出 schema、参数、权限和失败记录；不能用虚构专家角色封装执行。
2. 评审显式节点类型及版本，提供旧 tasks 草稿的读取兼容；配置进入计划等价比对与批准范围。
3. 在接入分流前定义 `skipped`、默认路径、汇合与缺省输出规则，再实现白名单结构化谓词。

验收：工具操作结果可追溯到输入及工具版本；失败不会伪装为分支 false；未选路径明确跳过，汇合不永久等待；重启恢复不重复已持久化成功操作；每条允许路径仍经过 W1 必需审查及系统确认。旧草稿、旧计划和现有 G1/G4 保持兼容。

P1 不在本轮执行，等待用户决定。
