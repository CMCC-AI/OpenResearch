# 科研工作流组件与自定义 Loop 设计提案

2026-11-11 · 设计评估已完成；以下实施计划待用户决定启动。

## 本轮目标与结论

- A：梳理非 Agent 组件。需要确定性执行、控制流、数据传递和人工介入，不能只扩展专家角色库。
- B：明确条件判断和脚本块边界。近期先用受限谓词实现结果门控，固定操作优先使用内置工具；沙箱脚本作为后续扩展，真实实验仍走现有运行契约。
- C：评估自定义 Agent Loop。支持用户组合有限的工作流循环；Agent 内部循环先按执行后端能力开放配置，暂不建设任意运行时代码插件体系。
- D：对照用户提供的另一份评估修订路线。采纳输入绑定、结果门控优先和脚本后移；保留执行状态与业务结论、技术重试与修订轮次的明确区分。

本提案没有变更运行代码、现有计划格式或已登记研究。下述结构均是建议，不能视为当前已支持。

## 长期组件取舍

下表说明能力边界，不代表首批都要实现。近期以现有任务模型上的输入绑定和结果门控为起点，见后文修订计划。

| 组件 | 科研用途 | 建议提供方式 |
| --- | --- | --- |
| 输入 / 输出 | 目标、材料引用、参数、最终交付 | 系统节点；提交运行时绑定具体输入，保留通用方法与运行配置分离。 |
| Agent | 文献理解、方案设计、写作、审查 | 保留现有专家与自定义 Agent；增加声明式输入和结构化输出。 |
| 工具调用 | 已注册检索、材料读取、解析等固定操作 | 独立节点，适合用户明确指定操作的场景；Agent 仍可在授权范围内自主选工具。 |
| If/Else / Switch | 数据是否齐全、审查是否通过、是否需要人工介入 | 先做依赖上的结果门控；出现真正的多路选择需求后，再提供受限谓词路由节点。 |
| 脚本 | 去重、统计、表格转换、规则评分 | 沙箱计算节点；先选一种运行语言，不为首版同时维护多套运行时。 |
| For Each + 汇总 | 每篇论文提取证据、每份数据独立分析 | 容器及显式汇总节点；配置并发上限、结果顺序和部分失败策略。 |
| Loop | 写作—审查—修订、检索—覆盖检查—补检索 | 带局部状态、退出条件及硬上限的容器。 |
| 人工输入 / 确认 | 补充材料、选择分支、判断是否继续 | 可暂停和恢复的节点；现有 G1–G4 仍为系统约束，不能通过删除节点绕过。 |
| 子流程 | 复用“逐篇证据提取”“独立审稿”等方法 | 循环容器底座稳定后开放；固定输入输出及版本。 |

重试、超时、取消、并发限制和日志是运行策略，不分别制作画布节点。普通并行依赖也无需强制增加“并行开始”节点。单次模型调用可作为后续轻量执行组件，暂不与 Agent 同时扩展，以免增加不必要的配置面。

## 条件判断

近期门控与未来分支应分开：门控只有“满足则继续、不满足则阻塞”，无需首先引入互斥分支和汇合。后续支持真正分支时，再实现跳过及汇合语义。确定性条件与语义判断分别处理：

- `eligible_count == 0`、`blocking_issues == 0` 等规则由引擎求值，不调用模型。第一版可用字段、白名单运算符和值的结构化谓词，无需通用表达式语言。
- “证据是否充分”由审查 Agent 输出经 schema 校验的判断、问题列表和证据引用，再由 If/Else 路由。该判断仍可能有误，应在运行记录中保留依据。
- schema 不合法、字段缺失或条件求值出错进入失败或人工处理路径，不能默认为 false，也不解析自然语言中的“通过”二字。
- 后续独立路由节点的各条件按顺序首个匹配生效，并有默认分支；需要同时激活多条路径时使用明确的并行语义。
- 未选中的路径标记为 `skipped`，不同于 `failed`。汇合节点等待本次实际激活路径，不能继续沿用“所有前置 completed”规则。
- 输出引用须通过作用域和路径校验：互斥路径不能读取彼此输出；跨分支读取必须先汇合并声明可缺省值。

## 脚本块

建议区分两种执行契约，即使以后共享底层执行基础设施：

1. **沙箱计算。** 显式 JSON 输入、schema 校验的 JSON 输出；文件以登记材料或产物引用传递。代码、依赖与环境固定版本，限制时长、内存和输出体积；默认没有宿主命令、凭据或任意网络权限。示例：论文去重、指标汇总、生成规范表格。
2. **项目命令 / 真实实验。** 需要项目环境、安装依赖、训练、GPU 或外部副作用时，接入现有 executor、Experiment/Run 和相应确认契约。是否属于实验由运行能力和用途校验，不依赖节点名称。W1 不能借脚本节点执行被预设禁止的实验。

近期优先验证固定工具是否能覆盖真实需求；出现固定工具无法覆盖的具体计算场景后，再评估 Python 沙箱。具体沙箱实现和依赖目录需在实施时依据现有执行后端核实。网络访问通过授权工具执行，避免脚本块变成另一套工具权限入口。

## 自定义 Agent Loop 的三个层次

### 1. Agent 执行策略

用户可以声明可用工具、结果 schema、上下文策略及执行预算。模型、步数上限、工具次数等配置按 harness 实际能力暴露；不支持的控制项须明确提示，不能保存后静默忽略。

这层控制单个 Agent 的行为，不要求用户把每次模型思考或工具调用都拖成节点。外层超时或取消可以限制整个调用，但不能伪称能够精确限制后端内部每个步骤。

### 2. 用户组合的工作流 Loop

应当支持。用户定义循环体、每轮输入、保留状态、退出表达式、最大轮数、累计预算及用尽后的处理路径。例如：

```text
输入目标与材料
  → 检索工具
  → 去重脚本
  → For Each（论文证据 Agent）
  → 汇总证据
  → Loop（最多 3 轮，示例上限）
       写作 Agent → 独立审查 Agent
       blocking_issues == 0：输出当前稿
       否则：带问题列表进入下一轮
       用尽轮数 / 预算：暂停，请人工决定
  → 引用审计
  → G4 交付确认
```

循环到达上限不等于审查通过。新一轮必须使用独立的轮次标识和产物版本，最后选择一个明确版本交付；后续引用审计如未通过，应阻止交付并进入明确的修订或人工路径。已经成功的论文提取结果无需因写作修订而全部重跑。

### 3. 用户自行替换 Agent 内部运行时

用户自己编写 planner、工具路由、记忆管理及每一步模型调用属于此层。暂不作为普遍用户的首批画布能力。只有明确存在无法用执行策略和循环子图表达的案例时，再评估版本化 Runtime 接口；研究性原型可单独验证，不能直接继承宿主权限。

这意味着产品应支持“我定义迭代方法”，首期实现无需承诺“我任意替换所有 Agent 的底层循环”。

## 必须先补的运行模型

- **工作流定义与运行实例分离。** 定义包含节点、控制边、数据引用、版本；实例绑定目标、材料、参数和批准快照。保留旧 `PlanInput` 与历史研究，不把复杂子图强行塞入 `role` 或 `brief`。
- **最小数据契约。** 第一版支持 string、number、boolean、object、array 和材料/产物引用；条件读取结构化输出，大文件通过引用传递。输出在消费前校验，执行数据不需要复制整份对话。
- **结构化子图。** 外层保持无环，Loop/For Each 内部有独立作用域；初期限制嵌套深度与总节点调用数。现有 40 个静态任务上限不能代表循环的实际执行预算。
- **执行标识。** 至少区分运行、节点、循环路径、列表项和 attempt；技术重试增加 attempt，语义修订增加 iteration，两者可分别统计和恢复。
- **持久化与恢复。** 保存输入输出摘要、产物哈希、分支决定、轮次状态和预算用量。模型与外部服务不保证逐次输出一致；恢复优先复用已持久化成功结果，不承诺重新执行得到相同文本。
- **副作用与取消。** 工具和项目命令采用幂等标识或外部状态核对，不能宣称任意外部副作用恰好执行一次；恢复和取消时核对仍运行的进程/任务。
- **科研契约。** 必需审查、引用审计、材料证据与 G1–G4 约束由服务端检查所有允许的执行路径；不可用分支跳过必需审查，也不可把模型的 passed 结果当作人工批准。
- **可观察性。** 画布展示实际选中的边、跳过原因、脚本错误、每轮输入输出及退出原因；调试支持查看输入和单步验证，避免只能通过整图重跑定位问题。

## 待启动的实施计划

目标：先让 W1 的输入和审查结论可被引擎明确消费，再支持受控修订，保持旧工作流和研究确认机制兼容。长期组件清单不作为一次性实现范围。

| 阶段 | 交付范围 | 验收标准 |
| --- | --- | --- |
| P0 输入绑定与结果门控 | 依赖产物引用、结构化 verdict、受限谓词、阻塞原因与主理人通知；不增加通用控制节点 | 下游得到明确的上游产物引用；审查任务完成且 verdict 为不通过时不得放行；缺失/非法 verdict 显式处理；结论绑定被审稿件版本。旧计划保持可推进，新字段影响去重和批准范围。 |
| P1 人工检查点 | 任意任务前后的暂停、批准、拒绝和恢复 | 决定绑定实际输入或产物版本；重启后仍暂停；重复批准不重复派发；不能替代或绕过系统 G1–G4。 |
| P2 有限修订 | 先提供写作—独立审查的声明式修订单元；引擎管理轮次、反馈、产物及预算 | 外层图无环；通过提前退出；修订不覆盖旧稿；技术失败仅重试对应步骤；耗尽上限升级人工且不标记通过；恢复不重跑已完成轮次。 |
| P3 场景驱动扩展 | 依据具体需求选择固定工具、For Each/汇总、独立路由或可编辑循环子图，不默认整批上线 | 每个组件有真实样例；路由的跳过与汇合正确；批处理有并发和失败策略；工具版本、参数与结果可核查。 |
| P4 按需评估 | 沙箱脚本、版本化子流程和更多 Agent 执行策略 | 先给出固定工具/既有执行能力不能覆盖的案例；验证隔离与部署；后端不支持的控制项明确反馈；预算、取消和记录贯穿调用。 |

贯穿验收：W1 不能通过脚本/工具/循环运行实验；必需审查不能被分支绕过；旧批准不适用于变化后的范围。按 `.github/workflows/ci.yml` 完成相应检查；若变更 UI，构建并纳入 `ui/dist`，使用隔离 slot 检查宽屏、窄屏及折叠侧栏。

首批不包含任意回边、无限循环、任意宿主 Shell、自定义运行时插件、外部 DSL 导入或定时触发系统。

## 对另一份评估的核对结论

以下针对用户粘贴的原文；未读取到原分享网页。

1. **认同结果门控先于通用分支。** [`research_finish_checked`](../../src/store/research.rs#L1321) 验收运行状态、产物与摘要，没有结构化审稿 verdict；完成审查工作与稿件通过审查需要分开。建议 verdict 使用 `pass / revise / blocked` 或同等明确枚举，执行失败单独记为 failed。阻塞可以暂时保留 pending 存储状态，但界面、原因、通知及恢复动作必须明确，不能永久静默等待。verdict 须绑定被审产物哈希和轮次，不能把旧稿的通过用于新稿。
2. **认同输入绑定优先。** [当前派发提示](../../src/commands/research_dispatch.rs#L149) 要求读取依赖产物，却未在这段构造中注入完整的上游产物映射。先提供来源节点、产物引用、哈希与版本，再逐步扩展通用变量端口；仍需证明实际读取，不能把注入清单视为已读。
3. **修正去重论证。** [`research_plan_equivalent`](../../src/store/research/plans.rs#L60) 比对摘要、流程、材料、完整任务规格和 Agent 快照；[`plan_summary`](../../src/workflow/mod.rs#L107) 主要由目标、流程、任务数生成。新字段必须进入完整规格的等价比对、批准快照与完成结果继承校验，仅使摘要确定性不足以保证兼容。内置工具也并非天然可审计，必须记录工具版本、参数、输入输出和副作用状态。
4. **不把 iteration 混入现有 attempts。** [自动恢复逻辑](../../src/commands/research_dispatch.rs#L388) 已按 attempts 决定补产物提示、重试或失败；混用会让正常审稿修订消耗故障恢复次数。可复用执行记录基础设施，但业务轮次与技术重试须分别标识。有限修订可先作为任务及评估者组成的封装单元，将来再开放循环体编辑；用户配置循环与引擎拥有执行权可以同时成立。
5. **不使用 LLM 求值固定谓词。** 白名单规则仍由引擎确定性判断并记录输入、规则版本及结果；语义评价由 Agent 产生结构化事实或结论。受限谓词同样需要审计，省去的是通用语言解析与能力范围，而非审计义务。
6. **轮数上限不等于成本上限。** G1 要纳入评估者、标准、可重复步骤、轮数、上下文及工具范围；还应给出时间/预算限制及后端实际可执行的约束，不能仅凭 `maxIterations` 承诺最大花费。
7. **脚本推迟是优先级判断，不是仓库归属禁令。** [`AGENTS.md`](../../AGENTS.md#L5) 明确本仓库负责本地编排与执行后端，伴随服务负责 sandbox provisioning 等服务能力。脚本执行及其契约未被一概排除；若实施涉及服务侧 provisioning API，须检查兼容且不得擅自改伴随仓库。“上传材料是数据”也不禁止用户另行明确授权的代码执行。

本轮据此修正首批范围与先后顺序，保留长期扩展方向；没有启动上述实施阶段。
