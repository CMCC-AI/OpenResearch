# 科研专家团融合最终方案与实现记录

## 1. 结论与适用范围

采用方案 C：**独立模式入口 + 单点专家会诊 + 共用 OpenResearch 执行底座**。

OpenResearch 已有的实验树、Git worktree、计算后端、Run、日志守护适合承担实验事实；CMCC 专家团的角色分工、任务契约、独立审查适合承担研究组织与质量控制。两者可以融合，不应迁移第二套计算 Run 或另建调度服务。

本次落地到当前 OpenResearch 仓库；CMCC 仓库仅作为角色规范来源，不修改其代码。前置流程对比见 [可行性分析](expert-team-integration-feasibility.md)。本文是实施版，以下修订优先于原始规格书中的示例。

## 2. 对原始方案的修订

| 原规格 | 最终决定 | 原因 |
| --- | --- | --- |
| 放开 OpenCode `question` 承担审批 | 使用平台自己的审批 API、SQLite 记录和页面卡片 | 提问事件不是授权事实；审批不应绑定一种 harness |
| 主理人通过 OpenCode `task` 调专家 | `orx research dispatch` 复用原生 helper session | 独立会话、worktree、并发限制和完成通知保持一致 |
| `orx exp branch`、传 command 给 `exp run` | `orx create-experiment` 建节点，`orx exp run <experiment-id>` 提交 | 原示例与当前 CLI 不兼容；运行命令来自实验/项目配置 |
| 代码变动也必须通过 `exp run` | 代码在 session worktree 中编辑并提交，只有实验负载通过 `exp run` | 代码编辑与计算提交是不同操作 |
| 固定全员流程 | 按需选择 20 个角色中的子集，注册有依赖的任务 | 控制成本和等待时间，不要求每次启用全部专家 |
| G4 发布确认 | G4 确认研究包版本；对外发布另行操作 | 下载归档不应隐含网站发布或外部发送 |
| 每任务任意多个 Run | 本版每执行任务一次精确授权、一次 Run | 防止重试和参数变化复用旧审批；多实验拆为多个任务 |

## 3. 产品流程

### 普通模式

保留原会话与实验循环。已有普通会话提供“方案设计会诊”“失败异常诊断”“独立审稿与引用核验”入口；点击创建同项目的新研究会话，原会话仍保留。

会诊以新的用户意图与项目材料为输入，不复制作者完整会话给审稿人。用户应在会诊目标中指定待审文件、实验或问题；目前不会自动把界面选中的 Run 作为结构化参数传入。

### 专家团模式

1. 新建会话选择科研专家团，输入目标。
2. 主理人盘点材料、生成任务 DAG，登记计划版本。
3. 用户通过 G1 批准目标、范围、产物与停止条件。
4. 主理人派发就绪任务；平台检查前置任务及文件摘要，每个任务创建独立 helper。
5. 实验代码提交后，主理人登记 Run 契约，用户通过 G2/G3。
6. 执行专家使用原生 CLI 提交 Run；平台校验实验、代码版本、命令、资源选项与任务身份，并在事务内登记一次提交。
7. 分析与写作专家登记产物和证据；独立审稿在待审材料完成后启动，引用审计依赖审稿，归档依赖审计。
8. 所有任务验收后申请 G4；用户查看材料、证据和草稿包，批准后下载正式归档。

调度由主理人 Agent 推进，平台负责依赖与授权检查，沿用原生 helper 完成唤醒。它不是一个脱离 Agent 自动执行任意 DAG 的后台工作流引擎。失败任务需要明确结束并修订计划，不静默无限重试。

非实验会诊只经过 G1/G4；设计、诊断、审稿会诊不允许提交实验。需要实际修复实验时建立完整研究计划。

## 4. 数据与一致性

| 实体 | 存储/关系 | 关键约束 |
| --- | --- | --- |
| Study | `research_studies`，关联项目与独立主会话 | 模式、目标、计划历史、决策与证据持久化 |
| Task | Study 的版本化计划中 | 有向无环、角色有效、输出路径唯一、最多 40 个任务 |
| Session 绑定 | `research_sessions` | 一个任务一个新会话，旧版本不能继续推进 |
| Experiment 绑定 | `research_experiments` | 实验属于同项目，绑定任务及计划版本 |
| HumanDecision | Study 内 | gate、version、scope、scopeHash、status、reason、approver |
| EvidenceClaim | Study 内 | 原文声明、实验关联证据或推测；实验记录真实 Run、commit、日志行与摘要 |
| 原生 Experiment/Run | 原有表 | 不建立第二套计算状态 |

Study 采用 JSON 聚合文档和 SQLite `BEGIN IMMEDIATE` 事务更新。派发 helper 和任务绑定同事务；预留 Run 和消费运行授权同事务，失败一起回滚。保留历史计划和决策，新版本不继承旧版授权。

计划修订要求现有 helper、任务与 Run 已结束；重复提交运行契约可重入，已派发任务返回原会话，重复提交 Run 被拒绝。停止研究会停止后续派发、取消待执行任务、请求取消 Run，并中断研究会话。

当前状态为 active/stopped，G4 表示当前包获批，不会自动把 Study 关闭。用户可继续制定新版本，或点击停止结束研究。

## 5. 审批边界

- **G1**：完整计划的范围摘要；每次计划版本更新重新确认。
- **G2/G3**：针对同一精确运行契约分别确认资源和执行。契约包含实验 ID、Git revision、运行命令、backend/host/flavor/image/manifest/container/timeout/disk/provider/org 等参数及配置摘要。页面可展开完整范围。
- **G4**：当前计划、已验收文件摘要、证据、Run 来源和日志摘要。审批后内容变化会阻止批准包导出。
- 用户点击写入平台记录后，通过持久消息恢复主会话；恢复失败不会撤销决策，可点击“继续研究”重试。
- CLI 没有 approve 命令，模型提示明确禁止伪造审批或调用审批 API。HTTP 写入要求同源浏览器元数据，并沿用现有应用访问控制。

**重要限制**：这是本地可信工作台中的工作流控制，不是针对同一 OS 用户下恶意代码的权限隔离。`Sec-Fetch-Site` 不能证明真人身份，拥有 shell/数据库写权限的程序仍可绕过。`approver` 当前记录 dashboard-user，不是多用户实名审计；若部署面向不可信 Agent/多租户，需要独立认证、不可由 Agent 写入的审批存储和执行凭据隔离。

G2/G3 当前控制正式实验提交，不拦截所有 shell、联网、安装依赖和数据下载。此类行为仍依赖 harness 权限和研究范围约定。预算是计划约束，不是计费系统的硬额度。

## 6. 专家、产物与证据

20 个 CMCC 角色规范随 `orx-research-team` 技能编译进程序。移除了 OpenCode 的角色包装，增加原生 CLI、worktree、统一产物路径和禁止子成员继续派发的约束；不要求用户手动挂载 CMCC 配置。

- `codeRoot`：当前会话的原生 Git worktree。
- `artifactRoot`：`<数据库目录>/files/<project-slug>/research/<study-id>/`，使用项目文件服务对应的持久目录。
- 输出必须为目录内的相对路径；拒绝路径穿越与逃逸 symlink。
- 验收检查声明文件存在、非空及 SHA-256，不将文件存在等同于学术正确。
- 实验声明必须引用同项目真实终态 Run 及有效日志范围；系统保存摘录和 hash。运行失败也可作为负面实验结果。
- 论文声明要求原文位置；平台不自动核实论文真伪、引用正确性或统计结论，仍需审查专家和用户判断。
- 审稿和引用审计使用不同新会话；依赖约束避免审稿先于材料，证据变化使既有审查失效。独立会话降低作者上下文偏见，不保证模型无偏见。

## 7. Research Package

支持草稿 ZIP 和经过 G4 的批准 ZIP，包含：

- `research-package-manifest.json`：研究目标、全部计划与审批历史、任务、证据和公开 Run 来源信息。
- `artifacts/`：当前计划已登记并通过摘要验证的产物，包括小型数据、论文、图表、审查报告等。
- `logs/`：关联原生 Run 日志。
- `sources/`：原生 Run 冻结的代码归档，按 digest 去重。
- `README.md`：解释研究包与科学有效性边界。

单文件上限 32 MiB、归档内容累计上限 128 MiB。大型外部数据集需要在产物中记录版本、来源和复现方法，不自动打包。没有实际运行的纯会诊不包含代码快照；批准包中的实际 Run 必须具备可用源码快照。旧计划保留元数据，但不自动纳入旧计划全部产物文件。
