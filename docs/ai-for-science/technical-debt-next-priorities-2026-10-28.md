## TD-15：调度线程释放了，续租调度仍依赖长工作结束

位置：`src/local/chat/mod.rs:10276` 的 `watch_runs`，`src/commands/up/research.rs:82` 的目录 gate；`src/store.rs:409` 的 60 秒租约 TTL 和 `:1690` 的 claim。

watcher 每轮先 sleep 3 秒、取得目录 gate、续租，然后依次 await run 唤醒、spawn 扫描、自动派发和产物验收，整轮结束后才安排下一次续租。这些阶段进入后台池后不再直接阻塞 Tokio 调度线程，但下一次 heartbeat 仍要等它们完成。轮次也持有目录 gate；人工确认会在同一个 gate 内校验交付文件和日志，存在额外的等待来源。

因此 3 秒不是心跳周期上界，实际间隔包含池排队、gate 等待、SQLite 等待、文件 hash 和原生发送准入等阶段。长任务本身不一定有问题，问题是它们承担了与租约生存期相耦合的调度责任。

故障边界探针：保留原进程的本地 busy 状态并阻塞一个扫描阶段；人为把持久租约 heartbeat_at 推到 TTL 之外，另一隔离 Store 连接可以获得相同会话的新 token；旧主机在阶段结束后续租得到所有权丢失。探针没有真的等待一分钟，没有启动两个原生模型，也没有证明线上存在该问题；它验证了超时后的抢占机制和本地忙状态不能阻止跨进程接管。

建议先记录真实的轮次、heartbeat 间隔及各等待阶段，随后让续租独立于长扫描/交付校验的完成，保持目录迁移保护和失去 token 后停止旧 turn 的规则。不能只扩大 TTL，也不能只新增 timer 却仍让它等待相同的长临界区。验证还应覆盖共享后台池满载时续租是否能及时执行。

验收：长扫描、多个大文件、目录 gate 争用、数据库忙和池满载下的续租间隔；两个 up 竞争时不重复执行存活会话；真崩溃仍可恢复，迁移仍须等待实际 worker。

## TD-05C：用户 Stop 的中断发生在清队列之后

位置：`src/local/chat/mod.rs:7004`，特别是清队列 await 后才调用 interrupt 的顺序。

真实写锁探针让 A 会话的忙入队持有全局 queue-persistence 并等待 SQLite；此时调用 B 的用户 Stop。B 即使没有运行中会话，40 ms 观察窗口内也不能返回，连 B 的 clear opener 都尚未进入。释放 A 的数据库锁后 B 才完成。同期 B 的 is_busy 可及时返回，说明前一批 turns 锁治理有效，但没有消除用户 Stop 的队列持久化等待。

活动 B 的原生中断同样排在这一步之后，这是源码顺序推导；本探针没有启动真实模型测量取消耗时。SQLite 写锁还可能直接拖慢 B 自己的 DELETE，不能只拆 mutex 就承诺即时停止。

建议把运行时中断、持久取消和历史收尾的职责及顺序明确化，评估会话级队列互斥，并让原生取消不必等待无关会话的落盘。保留取消持有计数、in-flight dispatch、提交前检查和故障恢复保护；若先中断后落盘，必须防止 queued 数据在重启或巡检中复活。不能通过清空内存而忽略磁盘失败来宣称取消成功。

验收：A 慢入队/慢重试期间 B 的真实 Stop/Escape、B 自己的数据库失败、重复 Stop、迟到失败派发、请求取消和重启恢复。

## TD-16：研究生命周期缺少产品入口

位置：`src/store/research.rs` 的创建/决策状态处理，`src/commands/research.rs:16` 的命令集、`src/commands/up.rs:511` 的研究路由、`src/store.rs:2345` 的删除保护。

复现：三个任务验收并批准 G4 后，study.status 仍为 active；调用删除主会话接口对应的 Store 操作，返回“研究仍处于活动状态”。这是删除保护在正确执行，缺少的是受支持的研究级状态转换。原生 CLI 没有 pause/stop/complete 等命令，研究 HTTP 路由只有查看与决策；本次检索到的 stopped 赋值均在测试中。

影响不止删除：已完成研究继续进入 active 列表和巡检；用户也缺少明确的研究级暂停/结束操作，不能把单个聊天的 Stop 当作暂停整个 DAG 的契约。

建议先定义“暂停调度”“结束研究”“停止已运行实验”“归档/删除”的区别，再实现合法转换。交付批准是否自动结束可以讨论，也可保留显式结束和后续新计划恢复。不要直接去掉 active 删除保护，更不能因用户结束研究而默认删除材料、Run 或日志。

验收：空计划、部分完成、等待 G2/G3、后台 Run、已交付、拒绝交付、结束后再修订、历史 stopped 记录；暂停后不继续自动派发，结束后允许受控归档/删除且保留引用。

## TD-05D：低频发布路径仍有全局阻塞

位置：`src/local/chat/mod.rs:4026`；`src/commands/up.rs:2156` 的旧 worktree 迁移调用。

`while_idle` 取得全局 turns 后逐会话打开 Store、检查持久租约，并在同一锁内同步运行 f。调用方 f 是 Git worktree 迁移。即使 session_ids 为空，回调也会在全局锁内执行。

单线程探针传入空列表和 70 ms 同步回调，确认回调期间 turns 无法获取，预先注册的 5 ms timer 被延后至少 60 ms。这里的毫秒数来自注入夹具，不是实际 Git 迁移性能；多线程生产 runtime 的其他线程可能继续运行，但依赖 turns 的请求仍受锁影响。

建议将真实阻塞工作移出异步调度线程，并用受影响项目/会话的迁移保护维持 worktree 生命周期。不能单纯在检查后释放 turns，否则新 turn 可能在迁移前启动。按实际发布使用频率排在发送/Stop/心跳之后。

## TD-17：历史 Run 与当前交付的引用范围需先统一

位置：`src/store/research.rs:1475` 的 `research_runs` 与 `:1377` 附近的 package 校验。

当前研究 Run 集合包含所有 plan 版本的 run_ids、previous_run_ids，以及所有 claim 引用。package 对该集合的每个 Run 都要求记录存在、状态结束、日志可读，并构造来源摘要。

探针构造全部任务完成、当前任务无 run_ids、claims 为空的研究；只保留一个 previous_run_ids 历史失败 Run。旧日志缺失时当前交付范围不能生成，补回同一个历史日志后通过。该行为已验证，但它可能是“完整研究审计包”的预期策略，不能未经定义就删除历史校验。

下一步应区分“当前结论引用闭包”和“完整历史审计集合”，明确历史日志缺失时的交付语义，再让 UI、统计、删除和磁盘回收使用同一规则。它直接约束后续 GC：不能仅按时间或旧版本身份删除日志。

## TD-18：证据摘录仍存在未限定的内存与写锁成本

位置：`src/store/research.rs:1352`，`src/commands/research.rs:52`。

上一批已把 package 的日志 hash 改为流式，但 `research_add_claim` 仍在 research_update 的 BEGIN IMMEDIATE 事务内读取完整日志，再创建所有行的引用数组。最多 201 行的约束限制行数，不限制单行/摘录总字节；文本和 source 也没有这里的容量上限。CLI 请求的 256 KiB 限制在 `std::fs::read` 后才检查。

大型日志会增加内存峰值、持有 SQLite 写锁的时间和聚合 JSON 大小。未在本轮故意生成超大文件或触发 OOM；这是源码确认的容量边界，不是当前内存故障诊断。

建议使用有界流式日志摘录与 hash，限制摘录和字段总字节，在写事务外完成长读取并于提交时验证来源仍一致；研究 JSON 读取采用有界 read。不能只在整份读取之后检查大小，也不能缩小日志范围却丢失既有完整日志 hash 语义。
