# 性能治理第七批：状态转换与用量结算（2026-10-23）

基线 `55ff9d3`。本批隔离共享 turn 收尾的完成/失败状态转换及用量结算，功能扩展和服务器部署继续暂缓。

## 改动

- `settle_turn_with_store` 将完成或失败状态转换移入现有 8 并发执行池。调用者等待该任务结束，再构造最终错误卡并执行第六批的最终消息落盘，之后才继续会话结束和队列处理。
- 状态转换成功后，复用同一个 Store 连接执行 `finalize_turn_usage`，减少原来成功转换后再次打开 Store 的开销。状态使用 `completed`/`failed`，用量结果使用既有 `done`/`failed`，不混用两套词汇。
- 转换仍依赖现有条件更新：只有 preparing/retrying/running 可变为完成或失败。已停止或已有终态的 turn 不会被迟到收尾覆盖；本任务没有赢得转换时不进行用量结算。
- 收尾时仅从内存移除 `turn-retry` 卡，随最终快照统一写入、广播；不再调用会同步更新 running 状态并额外 flush 的 `clear_retry_status`。失败卡仍只在失败转换成功后生成，重试耗尽遥测的条件保持不变。中间重试卡清除快照不再单独广播。

单个收尾任务内部按“状态 → 用量”执行，外层按“收尾任务 → 最终消息 → 会话结束”等待，没有新增未等待的后台收尾队列。两项数据库操作仍不是同一个事务；本批没有重写既有用量聚合或中断处理流程。

## 验证

新增三项回归：

1. 完成和失败分别验证：单线程 Tokio 的异步心跳能释放模拟慢 Store；存储工厂只调用一次；状态、错误类型、恢复动作和用量结果正确。重复转换不改变已结算结果。
2. 后台任务等待打开 Store 时，先将 turn 停止并结算 cancelled，再释放等待；迟到任务返回未赢得转换，停止状态和取消用量不变。
3. 打开失败时状态仍为 running、用量未结算；通过 SQLite trigger 注入用量更新失败，已成功的 completed 状态仍被调用者识别，用量保持待恢复；移除故障后，显式调用现有 `recover_terminal_usage` 可补结算。

最终验证通过：三项针对性回归；`cargo check --locked --all-targets`、`cargo fmt --all --check`、`cargo clippy --locked --all-targets -- -D warnings`、`git diff --check`；完整 `cargo test --locked` 退出 0，1213 项单元测试和 18 项集成测试通过，8 项专用测试按定义忽略。本轮未显式复跑忽略的性能基准和故障专用项，不将默认忽略视为已执行。

日志在忽略目录 `.mobilesci-run/backport-v0.2.20/acceptance/performance-settlement-*.log`：`tests` 为针对性回归，`full-tests` 为完整回归，`check`/`clippy` 为静态检查；源码及日志哈希见 `performance-settlement-evidence.json`。

## 边界与后续

- 本批验证异步调度可前进、单连接复用和状态/用量边界，未新增吞吐或尾延迟基准，不宣称具体提速比例。
- 用量结算仍沿用 best effort：失败不撤销已成功的状态转换，调用者仍继续最终消息写入。测试中的显式恢复不是每次失败均立即自动重试的保证。
- 若状态转换成功后并发中断与用量结算竞争，仍使用原有状态 CAS 和用量首次结算规则；本批不将状态与用量改为跨流程原子事务。
- turn 启动、上下文用量保存、目标事件文件处理、`finish_turn` 的会话/队列存储及中断清理仍有同步操作，继续排期；最终写入失败重试与磁盘满恢复边界也未关闭。TD-05 不整体关闭。
- 未改 UI、依赖和平台服务，未重启既有实例或部署服务器，未声称生产压力或完整跨平台 CI 通过。
