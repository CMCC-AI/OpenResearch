# 运行监控告警领取原子性（2026-10-29）

本批基于 `b78aeb3`。检查自动唤醒受理链路时发现，
`process_run_monitoring_alerts` 为同一会话合并通知多个失去监控的 Run，
但逐条更新 `monitoring_alerted` 后才发送通知。
如果后续某条 SQL 写入失败，函数直接返回，此前更新却已经提交。
对应 Run 尚未通知就被后续巡检当成已通知而跳过。

## 复现与最小修复

隔离子进程使用独立 `ORX_DATA_DIR`，为同一会话登记两个失去监控的 Run。
SQLite 触发器让第二条告警领取更新失败。修复前回归失败：
`a failed claim batch consumed an alert before notification`，记录为
`/tmp/orx-monitoring-before.log`。

生产代码只在现有领取循环外包裹 `begin_immediate`／`commit`：

- 同一会话的整组标记更新全部成功后才继续发送通知；任一 SQL 失败自动回滚。
- 沿用单条条件更新和既有通知合并、去重规则；其他进程已领取的行仍不重复领取。
- 事务仅包含数据库标记更新，提交后才调用异步聊天受理，不把发送或模型运行放进事务。
- 错误仍向 watcher 传播，工作线程退出后既有 TurnGuard 清理逻辑释放预留和租约。

这消除了实际可复现的部分提交窗口，没有改动数据库结构、公开 API、Run 状态、
监控错误文本过滤或通知消息。与逐行自动提交相比，同组更新还减少了提交次数。

## 回归边界

新增回归沿真实 watcher 告警处理路径执行，验证：

1. 第二条领取写入失败时，前两条均保持未通知；已通知的第三条保持原样。
2. 没有产生 chat turn，Run 仍为 starting；异步清理完成后会话不再 busy。
3. 移除故障后再次巡检，通过审计触发器确认前两条都能重新领取，第三条不会重复领取。
   测试刻意缺少项目，使隐藏续聊在调用模型前失败，随后沿既有逻辑重新武装告警。

没有调用模型、连接远端计算、修改真实数据或部署。此修补处理的是**领取阶段的 SQL
部分提交**；领取已经提交后进程崩溃，或发送失败后的重新武装写入失败，仍属于现有
布尔标记投递语义的限制。本轮没有把标记扩展为通用通知队列；若要保证跨崩溃重投，
应先明确重复通知与至少一次投递的契约，再决定是否需要持久投递状态。
