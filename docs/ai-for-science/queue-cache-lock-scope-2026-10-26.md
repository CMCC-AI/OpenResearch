# 队列缓存锁范围治理（2026-10-26）

本地基线 `cd2cd14`，Rust 源码与上一批 `f4bca06` 相同。首页已有独立提交及其他界面/构建资源的工作区改动，本批不改写或提交这些文件。产品版本和 partial 上游状态不变。

## 核查与取舍

忙队列的 `persist_busy_submission`、取消单条消息和手动重试，原来均持有 `queued` 的全局同步 mutex 执行 SQLite 写入。即使写入已经进入后台池，异步路径的 `queued_items` / `queued_count` 等读操作仍可能等待该 mutex，从而把慢存储重新传导到调度线程。

取消/重试 API 已经通过 `blocking_api` 进入有界后台池，本批复核后保留该入口，不增加重复 offload。全局 turn-map 及 plan/permission revision 锁跨 SQL 涉及准入、设置顺序和失败回滚；本批只缩小可以由现有 queue-persistence 锁保障的缓存锁范围，不直接拆开所有全局锁。

## 改动、原因与影响

| 改动 | 原因与实现 | 影响范围 |
| --- | --- | --- |
| 忙队列写入后再锁缓存发布 | queue-persistence 与现有 turn/revision 锁仍保证写入顺序；事务提交前不需要独占队列缓存 | 慢入队时，其他会话及本会话的队列读操作能返回旧的已提交状态；成功后才出现新项 |
| 取消消息分成短快照、SQL 删除、短缓存更新 | 同一 queue-persistence 临界区保持目标稳定，不必让读者等待 DELETE | 删除成功前原消息仍可见；失败保留原队列，不发成功广播 |
| 手动重试分成头项快照、SQL 更新、短缓存替换 | 保持只允许耗尽的队首重试，沿用原幂等键及 Store 更新方式 | 保存成功前仍显示旧耗尽状态；保存失败不提前清零尝试次数或解除抑制 |
| 私有 Store opener 与独立回归文件 | 复用真实 SQLite 锁与失败注入，避免扩展生产 API | 无 HTTP 字段、审批规则、模型行为或 UI 变化；不新增锁表、线程池、重试机制 |

缓存修改仍由 queue-persistence 串行化；SQL 期间释放的是供读者使用的缓存 mutex，不是所有队列操作的互斥保护。worker 正常返回或等待者取消后的持久化、缓存发布与事件顺序保持不变。

## 验证

新增三个测试，包含六组真实写锁/失败场景及边界检查：

1. 忙入队成功和 SQL 触发器拒绝：由另一 SQLite 事务持有写锁，确认实际 worker 等待时缓存 mutex 可获取、旧队列可读、尚无广播；取消等待者后再释放写锁，检查成功发布或事务/revision 回滚。全局 turn-map 在此期间仍被占用，测试明确保留这一未解决边界。
2. 取消/重试各自成功和触发器失败：读者在真实 SQL 等待期间仍可读取旧项；取消请求等待者后检查实际落盘、缓存、抑制标记及广播是否一致。测试阻止恢复合成项触发默认 Store 的真实派发。
3. 非耗尽、非队首、目标不存在、已在途或已取消的重试/取消条件：返回值、队列条目数和原有拒绝行为保持不变；被阻止的重试不打开 Store。

## 剩余技术债与下一步

- **P1：全局 turn-map 与 plan/permission revision 锁仍跨 SQL/后台池排队。** 同会话顺序与失败回滚依赖这些锁，后续需按 session 隔离或归属验证后才缩小；不能把本批缓存读可用当作准入/Stop 已无跨会话等待。
- queue-persistence 仍覆盖 SQL；其他尚在异步线程内直接取得它的调用仍可能等锁。出队、清理与 guard 提前 Drop 等入口仍需核查。
- 已有 API 的初始元数据读取、压缩/扫描、持久化故障收敛、材料恢复与磁盘引用保护，继续按[统一技术债清单](technical-debt-progress-2026-10-26.md)处理。
- 固定候选真实登录/模型与服务器验收仍待完成；本批不重启当前服务、不部署、不改已有界面内容。Rust 构建使用工作区现有 ui/dist，不将其视为本批已验证的发布产物。

下一步优先建立全局 turn/revision 锁在多会话下的等待基线，明确 Stop、自然完成与重复 client turn 的互斥边界；在此之前不为缩短锁而提前发布未提交的队列项。
