# 技术债修复停止节点（2026-10-30）

用户要求明确本轮修到何处停止。本节点以 `ca04531` 为基线，范围固定为：
**运行完成通知、专家父会话通知和监控失联告警，在中断恢复时复用持久受理回执；
未受理的告警可以继续重试。通过故障回归、完整 Rust 检查并提交后停止本轮治理。**

这里“投递成功”指通知已有持久 chat turn，包含 preparing、失败或被中断后可恢复的
turn。它不保证模型成功回答，也不自动重跑已受理但执行失败的模型轮次；这些沿用
既有聊天恢复和显式重试入口。不能把通知幂等受理描述为原生模型恰好一次执行。

## 范围内的最小处理

- 运行完成与专家通知使用固定的内部 client_turn_id，复用已有 turn 唯一约束和查询。
  领取过期或确认 SQL 失败后，恢复先查回执，已有受理只补记通知状态。
- 共用私有 `deliver_notification`，发送前检查回执，发送返回后再核对回执。
  受理后启动准备失败仍保留原 turn，不通过新建轮次重复投递。
- 专家完成通知已有回执时直接结算，不重复解析摘要或重新执行科研收尾。
- 监控告警增加一个可空 monitoring_delivery_id，保存合并通知的批次身份。
  先原子保存批次，再发送；中断或复位失败时，即使 alerted 为 true，待投递批次仍会重试。
- 告警已有回执时，同一 SQL 更新整组确认标记并清除批次身份。
  监控恢复时清除标记及身份，之后再次失联生成新批次，避免被旧回执误去重。
- 采用已有版本化列迁移 `monitoring-delivery-v1`，没有新增任务表、执行池或消息中间件。
  删除运行唤醒受理后被忽略错误的重复 reopen；实际开始轮次时仍由既有事务处理该状态。

## 验收清单

停止前必须全部满足：

1. 运行完成通知已有 preparing／completed 回执后，过期恢复不会新增 turn。
2. 专家正常完成与启动失败通知已有回执时正确结算；确认失败、摘要随后损坏也可恢复。
3. 告警在批次持久化后、受理前中断，不会永久跳过；复位写入失败后仍能继续重试。
4. 告警受理后确认写入失败，恢复只补记；监控恢复再失联使用新的批次。
5. 首次发送在 turn 插入前失败时没有回执，可重试；插入后、模型启动前失败保留同一回执。
6. 可空字段升级幂等；旧记录不凭空生成投递回执；原有队列、租约和研究回归保持通过。
7. 完整 Rust、Clippy 全目标、构建、格式及差异检查通过，提交后工作区干净。

测试使用独立 ORX_DATA_DIR 子进程、真实 SQLite 触发器和重连模拟中断断点。
先预置 6 条回执验证运行、专家、告警恢复后仍为 6 条；首次发送的失败／重试再增加
且仅增加 1 条。模型启动前的 usage 插入触发器构成失败屏障，execution 数为 0。
这些是本地故障回归，不是实际 SIGKILL、断电、真实模型或服务器验收。

- 不部署、推送、重启真实服务或发起真实模型／实验。
