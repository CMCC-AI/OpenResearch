# 平台托管空间：产品与实现规划

> 适用范围：早期团队/托管方案的历史参考。当前本地版和服务器私人托管版的区别见[统一约定](../product/runtime-and-deployment.md)，现行托管权限见[私人空间权限](../product/private-space-permissions.md)。保留执行器实现不等于继续提供历史团队功能。

状态：第一阶段本机 Docker 原型已实现。现有自有执行器接入继续有效；公网服务仍按后续阶段建设。

## 本机启用与验证

在仓库根目录构建 `docker build -f packages/platform/Dockerfile.executor -t openresearch-managed-executor:local .`，然后在 `packages/platform` 运行：

```sh
docker compose -f compose.yaml -f compose.dev.yaml -f compose.managed.yaml up -d --build
```

创建空间默认选择“平台托管”。后台 provisioner 通过持久任务表管理容器，自动写入权限0600、所有者UID1000的凭据文件。无需向浏览器返回 token。当前限制4个托管空间，每个1 CPU / 1 GiB内存。`compose.managed.yaml` 是 localhost 团队原型配置，迁移服务器时须调整平台连接和文献地址。

仅独立供给服务挂载 Docker socket；它拥有宿主容器管理权限，必须限制为可信部署者管理。门户没有 Docker socket。供给事务行锁协调删除、重试与创建；失败需要显式重试。10秒周期对账维护环境健康状态，页面同时检查通道在线。该原型尚无模型自动授权、配额计费或公网强沙箱。

删除空间会异步停止并移除容器，数据卷 `orx-managed-<空间ID>` 保留。原有自有设备空间的文件和执行器进程不由供给服务管理。不要将门户删除理解为研究数据彻底擦除。

回归：`npm test`、`npm run test:integration`。实机测试 `node test/managed-smoke.mjs` 需专用开发 `DATABASE_URL` 及有效 `DOCKER_SOCKET`，会创建两个随机测试空间，检查连接和研究数据隔离，再清理测试容器、测试卷和临时数据库 schema。正式空间不受测试影响。

## 产品决策

默认旅程为登录 → 创建空间 → 环境准备中 → 进入科研工作台。用户不接触连接 token、终端命令、Docker 或连接器进程。平台部署者配置一次资源池，平台按空间自动准备运行环境。

自有设备接入保留为高级选项，适合实验室私有数据、GPU 或本地工具。它与平台托管是两种运行方式，不是账户登录配置。同一空间全体成员共享运行环境；邀请成员不创建执行器。一个账户在不同空间可以有不同权限。

## 为什么保留按空间隔离

当前 orx 的 SQLite、文件、Git、终端与 Agent 服务没有跨租户访问隔离。成员可能运行代码，单靠门户过滤 workspace_id 无法隔离同一个进程可读取的文件和凭据。因此当前阶段每空间使用独立环境与存储；资源可来自同一服务器，不需要每空间一台物理机器。

一个宿主代理可以管理多个隔离环境，但不能让多个空间共享同一个 orx 实例。连接器数量属于内部实现，不应成为用户操作步骤。平台托管环境未来可以改为内部认证路由，自有设备仍可使用主动出站连接。

## 分阶段交付

### 第一阶段：可信团队的单机自动托管

- 提供服务端能力查询；资源池未启用时明确显示不可用，不展示无法兑现的“立即使用”。
- 创建空间时选择运行方式。托管默认值只在资源池启用且容量可用时成立。既有空间保持原运行方式，不自动轮换凭据或迁移数据。
- 在同一数据库事务中创建空间和供给任务。重复点击、任务重试不得创建多个环境。
- 独立供给进程管理固定版本执行器镜像、空间专用容器和持久卷。公开网关不挂载 Docker socket，不接受用户提供的镜像、宿主路径或启动命令。
- 供给进程自动生成并安全安装空间凭据，配置本机连接地址与文献服务地址，凭据不返回浏览器。为 Linux 明确处理文件所有权，不能仅依赖 Compose bind secret 的 uid 配置。
- 状态区分排队、准备中、就绪、失败、已停止、删除中。展示失败原因、重试和容量提示；只有 OpenResearch 健康检查成功后进入就绪状态。
- 提供幂等任务领取、事务锁释放后的恢复和状态对账。服务重启不丢任务；创建成功但回写失败时发现并接管已有环境。
- 删除托管空间先撤销访问、排队停止环境，再完成资源回收；保留数据策略明确，不能沿用直接删除数据库记录后丢失容器归属的流程。

### 第二阶段：运行可靠性

- 分层健康检查覆盖连接通道、OpenResearch、Agent 工具、模型授权和文献服务。
- 重启、停止、日志与环境升级入口；凭据自动轮换和临近到期告警。
- 磁盘、内存、并发任务配额和空闲环境管理；暂停环境必须说明对运行中实验的影响。
- 备份恢复、归档与保留期，先验证恢复再承诺可靠性指标。
- 邀请邮件与账户恢复依赖实际邮件服务配置，不将生成链接描述为邮件已发送。

### 第三阶段：公网服务

- 为不互信用户引入独立 VM 或强沙箱、网络出口限制与秘密管理。普通 Docker 容器不作为公网恶意代码的安全边界。
- 资源池扩展、任务调度、多网关连接路由；避免当前内存通道表导致多副本路由失败。
- 用量、预算上限、审计与运营告警；购买资源和模型费用需要单独确定预算。

## 第一阶段验收

1. 新用户只填写空间名称即可获得可用工作台，浏览器不显示执行器凭据。
2. 两空间分别创建项目和文件，验证目录、SQLite、凭据及终端互不可见。
3. 同空间第二位成员加入后直接共享已有环境，不生成新执行器。
4. 网络中断、供给进程重启、镜像拉取失败、容量不足均有可恢复状态；重试不重复分配资源。
5. 删除与供给并发、重试与删除并发时，不遗留未管理容器，不误删另一空间数据。
6. 既有自有设备空间不受影响，成员与只读权限检查继续有效。

## 部署选择

第一阶段可在当前本机 Docker 验证完整流程，再将供给进程迁移到可信团队服务器。直接部署已有服务器需要明确服务器访问方式、容量、持久存储和模型授权来源。上线前须选择部署目标，不能把个人电脑的工具凭据隐式共享给所有托管空间。
