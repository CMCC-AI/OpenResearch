## 第一批：#771 选择性适配

固定来源为 [官方 #771](https://github.com/alphaXiv/OpenResearch/pull/771)，提交 `41db8ef22036b2e7232cd79e42403a41edc0a4bb`；实现及 HTTP 回归与正式版 `15f2b59bda0208dbaba536adb253cb8dc1ff7d62` 中的对应逻辑核对。仅择取 OpenCode V2 目录就绪及设置选择保留，不更改产品上游祖先、产品版本、更新通道或其他本地执行边界。

- `src/local/harness/opencode_v2.rs` 对模型／集成目录的 503 仅在 JSON 同时包含 `_tag: ServiceUnavailableError` 和 `service: plugin` 时等待重试，间隔 200ms。legacy 的 await-activation 仍仅执行一次。整段发现沿用 30 秒总期限，慢请求不会另起一段期限。
- 只有两个目录均成功且 `data` 为数组时才保存快照。非 legacy 的空模型目录继续轮询；插件重载或截止时可返回此前完整目录，禁止把新模型与旧集成拼成半份结果。此前无完整目录时，分别报告插件激活未完成或目录发现超时。
- 其他 503、401、畸形 JSON 和非数组目录立即失败，错误包含端点、状态及有界单行正文。设置页继续使用现有 agentNote 展示诊断；目录首次稳定后固定选中项，刷新失败或其他智能体就绪不会改变当前选择。保留本地账号／管理员配置权限判断。

HTTP 回归覆盖两种 V2 协议、两个目录的插件激活、不可重试错误、卡住的请求、总期限、冷目录及最后完整快照。设置页回归执行实际组件的 Hook 前缀，覆盖冷启动默认选择、刷新后选择保留和用户显式切换。

验证通过：Rust 全量 1343 项单元测试和 18 项 CLI 集成测试（另有 11 项既有忽略）；目录发现定向过滤实际执行 14 项，其中 5 项为 OpenCode 目录 HTTP 用例；前端全量 485 项测试，查询使用方定向 12 项。另通过 Rust 格式／Clippy／普通构建、UI 类型／i18n／样式／生产构建和体积预算，以及产品版本／真实上游祖先检查。`ui/dist` 已按本批源码重建。

本批不调用真实模型、不重启开发槽、不部署私人执行器。测试模拟的插件响应不是生产冷启动验收；其他官方 PR 仍按上表后续批次处理。

## 第二批：#776 发送准备与本地错误

依据 [官方 #776](https://github.com/alphaXiv/OpenResearch/pull/776) 和已固定 v0.2.22 源码中的发送前历史等待逻辑，适配本地 workspace/runtime、会话删除与虚拟消息行架构，不引入官方 response grouping。

- 发送前的历史查询遇到 TanStack `CancelledError` 时，在原作用域及原目标会话内重新等待；退出作用域或会话删除后停止，成功返回后也再检查删除状态。其他网络、权限及数据错误直接进入既有失败处理。
- 被取消的历史修复可能已经发布中间缓存。重试必须强制重新读取或等待正在执行的修复，不能仅因缓存存在就提前生成乐观消息。连续取消之间让出事件循环，使作用域退出和删除能够被及时观察。
- 本地 reducer 使用独立 `local_error` 标记，工具行直接渲染提示及具体错误，不再套用模型“轮次未完成”、额度或恢复状态。保留前一条模型回答和当前分支关系，仍由既有逻辑在服务端消息到达时清理临时消息。草稿、材料、注释和发送目标仍使用既有捕获／恢复规则。

回归使用实际 QueryClient 的取消行为，覆盖首次历史、已有中间快照、连续取消、作用域退休、删除、成功后删除、不可重试错误；同时执行 reducer 与真实提示行的 JSX，检查旧回答保留、错误归属和正文转义。查询使用方定向 17 项、前端全量 490 项、类型／i18n／样式／生产构建和体积预算通过，`ui/dist` 已重建。

本批未改 Rust 业务逻辑，不重跑上一批完整 Rust 套件。可控查询取消复现不等于已验收真实 SSE 断网、真实模型发送或服务器部署。投递结果不确定、steering 回执及 busy 归属判断仍属于下一批 #803，不将本次取消处理宣称为投递协议已完成。

## 第三批 A：普通发送与队列的请求归属

此批适配本地已有的普通 turn／队列幂等记录，解决“其他 turn 正忙就把本次发送当作成功”的问题；不是完整回移 #803，也不实现 steering 接收确认。

- 新增 `GET /api/chat/sessions/{id}/submissions/{clientId}`。在有界后台存储任务中验证会话及项目存在，再按 `(session_id, client_turn_id)` 查询。返回原会话 ID、原请求 ID，以及 `{kind: turn|queued, id}` 或 `null`。只投影身份字段，不读取或输出请求正文、材料、settings JSON 或 hash。单个 SQL 快照跨两张既有表查询，排队晋升期间优先返回 turn，无需新表或迁移。
- 回执表示本服务器已登记请求，不表示模型执行成功。`null`、缺少新接口、网络错误、无效／串号回执均表示结果未知，不能据此宣称服务端拒绝。回执查询禁用浏览器缓存，单次最多等待 3 秒并中止超时请求；不循环查询或自动重发。
- 普通发送／队列丢回包后，仅以匹配的持久回执确认归属，替换旧的 busy 推断。确认后重读原会话；未知时保留草稿及本次内存请求身份，显示“尚未确认”，不把其他 turn 的 busy 状态清掉。401／403／404／409／413／415／422／429 走明确拒绝处理；当前发送 API 还会将内部／准入失败映射为 400，所以 400、408 和 5xx 仍需核实回执。拒绝后也刷新实际会话状态，不替其他请求设置 busy=false。新增 HTTP 错误类型保留状态码，保持文件版本冲突的专用异常。
- 请求签名包含工作区／项目查询身份和目标会话。相同内容重试保留原请求 ID 及普通／steering 投递模式，不能因为当前会话变忙就把普通重试改成 steering。首次创建会话时在导航前绑定目标，避免 activeId 的重置 effect 清空请求身份。会话、视图、运行身份退出或删除后，查询结果不能恢复／清空新界面的草稿。

边界：待确认身份只在当前组件访问期内保存；刷新、往返会话后恢复尚未完成。steering 没有持久回执时仍返回未知，不用 turn／队列回执冒充 native steer 接收；其安全重试和跨通道去重留给下一批。普通队列被 Stop 清除后，缺少回执也不能被解释为该请求从未发生。现有材料上传缓存、workMode、store 有界池、原生取消及后台续租保持原有实现。

回归覆盖队列晋升、两表短暂共存、重开数据库、跨会话同名请求、HTTP 会话／项目边界及正文不泄露；前端覆盖匹配／串号／缺失回执、查询超时、作用域退出、明确拒绝、未知时保留草稿、确认时不恢复旧草稿、busy 状态不充当回执，以及普通重试与新建会话的身份保持。测试不调用真实模型；源码和受控 HTTP 验证不等于已部署真实弱网验收。

验证通过：Rust 全量 1345 项单元测试及 18 项 CLI 集成测试，另有 11 项既有忽略；前端全量 499 项测试。新增持久回执／HTTP 回归已实际执行；另通过 Rust 格式／Clippy／普通构建、前端类型／i18n／样式／生产构建、资源预算及产品版本检查。已重建 `ui/dist`；未重启当前开发槽，未部署新后端。旧后端缺少查询接口时，前端保守显示结果未知，不恢复旧 busy 推断。

## 第三批 B：steering 持久登记与跨通道去重

实现与验证边界见 [steering 回执记录](steering-receipts-2026-10-28.md)。在原生通道交接前登记 `(session_id, client_turn_id, request_hash)`，保留原始请求；重试查询原回执，原生明确拒绝时以原 ID／hash／设置回退排队。普通发送、排队与 steering 在 SQLite 写边界互斥，Stop 清除队列后保留 steering 登记以防旧请求复活。

回执表示服务端登记，不表示模型已接收或执行成功。原生交接超时／传输失败保留未知状态，不自动重放；进程崩溃后的不确定登记也不自动重放。浏览器刷新与离开会话后的 pending 身份／草稿恢复仍留给下一批。此批在后续开发分支实施，不修改已发布标签，也不表示已部署新后端。

## 第三批 C：待确认请求跨刷新恢复

实现与边界见 [待确认请求恢复记录](pending-submission-recovery-2026-10-29.md)。IndexedDB 保存原请求身份、草稿与附件、首次传输参数和材料引用；刷新／返回会话先查登记回执，未知时保留原 ID 和模式，已登记时不恢复旧草稿，保留核查期间的新编辑。写入／清理按账号、运行时、项目及会话隔离，并处理 logout、并发页面和迟到回包。

原生浏览器验证覆盖整页刷新和 6 MiB 文件；不自动重发，不重新上传已登记材料，不重复切换 `/plan`。普通未发送草稿仍沿用现有内存 stash。下一项是中文产物相对链接的解码与编码统一，再推进材料任务输入身份。

## 第三批 D：产物阅读链接的必要修复

优先级 P2：实际 `ArtifactMarkdown` 经 Markdown 渲染及 `artifactUrl` 构造后，`结果.md` 会变为服务端路径 `reports/%E7%BB%93%E6%9E%9C.md`，无法对应 `reports/结果.md`。影响中文、空格及保留字符文件名的链接／图片，也会使预览文件版本匹配失效；这是产物阅读故障，不是布局或代码风格优化。

仅将 `ArtifactsTab.tsx::artifactTarget` 的重复路径解析替换为既有 `resolveMarkdownTarget`，使文件名解码一次后再构造 API URL；保留现有 query／hash、版本参数和外部链接行为，并继续拒绝越根路径及非法编码。业务源码增加 4 行、删除 22 行，不新增模块、API、数据库字段或依赖。回归执行真实 Markdown 渲染和现有 URL 构造函数，先复现故障再验证修复。

验证通过：前端全量 521 项测试，类型／i18n／样式／生产构建及资源预算检查；`ui/dist` 已重建。日志位于 `/tmp/mobilesci-artifact-before.log`、`/tmp/mobilesci-artifact-targeted.log`、`/tmp/mobilesci-artifact-ui-all.log` 和 `/tmp/mobilesci-artifact-build.log`。未改变 Rust 或部署，不重跑无关后端测试。下一批优先核查材料输入变化后的旧结果继承风险，先复现再决定最小修复，不直接展开生命周期、回收或大模块拆分。

## 第四批 A：固定共享材料输入（2026-10-29）

P1 正确性问题已复现：更换主会话材料后修订相同任务，旧产物和审查仍被继承；计划批准后更换材料，待派发专家又会读取新材料，混用旧结果和新输入。修复前 3 项复现测试全部失败。

复用现有封存材料包身份，只在 `ResearchPlan` 增加可缺省的 `materialIds`，由服务端按主会话当前分支记录并纳入 G1；派发使用计划中的集合。材料集合改变时不继承旧任务，重复引用同一包或未选中分支的材料不触发重做。材料包沿用既有不可变／哈希契约，不创建版本服务、不新增表或任务材料选择器，也不在写事务中重新读取所有原件。详见 [材料输入契约](material-inputs.md#研究计划的输入范围2026-10-29源码实现)。

旧记录缺少该字段时保留原审批 hash；若当前存在材料，派发明确要求修订计划并重新确认 G1，不替历史审批补签输入。无材料的旧计划保持兼容；旧材料计划首次修订无法证明原输入一致时不继承完成结果。历史计划、审批和原件均保留，不中断已运行的专家或实验。
